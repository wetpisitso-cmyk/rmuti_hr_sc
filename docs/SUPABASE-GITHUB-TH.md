# วิธีเชื่อม Supabase และจัดเก็บซอร์สใน GitHub เมื่อพร้อม

ชุดดาวน์โหลดเริ่มที่โหมดทดลอง การเปิดหน้าเว็บในโหมดนี้ไม่มีขั้นตอนสร้างโครงการออนไลน์ ใช้ขั้นตอนต่อไปนี้เฉพาะเมื่อต้องการทดสอบฐานข้อมูลจริง

## 1. เตรียมโครงการทดสอบของวิทยาเขต

สร้าง Supabase Project ใหม่สำหรับระบบสารสนเทศบุคลากร เช่น `rmuti-kkc-personnel-mis-test` ฐานข้อมูลและสิทธิ์ของระบบนี้ออกแบบสำหรับโครงการแยกจากระบบรับสมัครงาน HR_KKC เปิดใช้ Data API สำหรับ schema `public` เปิด Email/Password ใน Authentication และเตรียมบัญชีสำหรับผู้ทดลองผ่านเครื่องมือผู้ดูแล

## 2. วางฐานข้อมูล

เปิด **SQL Editor → New query** คัดลอก SQL จากแต่ละไฟล์มารันแยกกันตามลำดับ

| ลำดับ | ไฟล์ | ผลที่ได้ |
| --- | --- | --- |
| 1 | `supabase/01-schema.sql` | ตารางสมาชิก ข้อมูลส่วนตัว ลายเซ็น ครุภัณฑ์ ผลประเมิน คำขอ คำสั่ง กิจกรรม การจองที่นั่ง และบันทึกผลงาน พร้อมสิทธิ์ RLS |
| 2 | `supabase/02-documents.sql` | Bucket ส่วนตัวชื่อ `hr-certificates` ให้ HR แนบ PDF และให้เจ้าของคำขอเปิดไฟล์ที่ส่งมอบแล้ว ขั้นตอนนี้ใช้เมื่อจะส่ง PDF ผ่านเว็บ |
| 3 | `supabase/03-catalog.sql` | รายการเส้นทางสังกัดของวิทยาเขตขอนแก่นสำหรับทดลอง |

ไฟล์ 01 และ 02 ใช้ครั้งเดียวต่อโครงการว่าง แต่ละไฟล์ทำงานเป็นธุรกรรมเดียว หากชื่อโครงสร้างมีอยู่แล้ว ให้ตรวจว่าเลือกโครงการทดสอบถูกต้อง รายชื่อสังกัดในไฟล์ 03 ควรให้หน่วยงานตรวจทานก่อนเปิดใช้งาน ใส่หนึ่งแถวต่อหนึ่งเส้นทาง วิทยาเขต → คณะหรือหน่วยงาน → กลุ่มสาขาหรืองาน → สาขาหรือแผนก

## 3. จัดทำบัญชีทดสอบสองบทบาท

1. ใน **Authentication → Users** สร้างบัญชีทดสอบด้วยอีเมลและรหัสผ่าน ยืนยันอีเมลสำหรับบัญชีทดสอบตามตัวเลือกใน Dashboard สร้างอย่างน้อยหนึ่งบัญชีบุคลากรและหนึ่งบัญชีเจ้าหน้าที่ HR
2. เปิด `supabase/04-provision.example.sql` แทนอีเมลตัวอย่างด้วยอีเมลของบัญชีแรก และกรอกคำนำหน้า ชื่อ นามสกุลสำหรับทดสอบ ใช้ค่า `staff` แล้วรันใน SQL Editor
3. ทำซ้ำสำหรับบัญชีเจ้าหน้าที่ โดยเปลี่ยนค่าเป็น `hr` สำหรับเจ้าหน้าที่ที่ได้รับมอบหมาย บัญชีที่มีเฉพาะ Auth แต่ยังไม่มีทะเบียนบทบาทและข้อมูลส่วนตัวจะเข้าหน้าบุคลากรไม่ได้
4. ถ้ากำหนดให้ HR จัดทำบัญชีทั้งหมด ให้ปิดการสมัครด้วยตนเองใน Authentication และใช้การสร้างบัญชีจากผู้ดูแล ชุดนี้ใช้หน้าล็อกอินอีเมลและรหัสผ่าน การเชื่อมบัญชีมหาวิทยาลัยแบบ SSO ต้องกำหนดร่วมกับผู้ดูแลระบบของมหาวิทยาลัยเพิ่มเติม

## 4. เชื่อมหน้าเว็บบนเครื่อง

ใน Dashboard ดู Project URL และ **Publishable key** ของโครงการทดสอบจาก **Connect** หรือ **Project Settings → API Keys** เปิดไฟล์ `web/config.js` แล้วแก้สามค่าต้นไฟล์ โดยคงรายการตั้งค่าอื่นไว้

```js
mode: 'supabase',
supabaseUrl: 'https://YOUR-PROJECT-REF.supabase.co',
publishableKey: 'sb_publishable_REPLACE_WITH_PROJECT_KEY',
```

ใช้เฉพาะคีย์ที่ขึ้นต้นด้วย `sb_publishable_` เพราะหน้าเว็บส่งไฟล์ตั้งค่าไปยังเบราว์เซอร์ เก็บรหัสผ่านฐานข้อมูล Secret key และ Service role key ไว้ฝั่งผู้ดูแล เปิดหน้าเว็บผ่าน localhost ตาม README แล้วรีเฟรช หน้าล็อกอินจะแสดงแทนปุ่มสลับบทบาท ระบบจำเซสชันในแท็บนั้น เมื่อจบการใช้งานให้กดออกจากระบบ

แก้ `contactText` เป็นเบอร์ติดต่อ สถานที่ หรืออีเมลที่วิทยาเขตรับรอง กำหนดลิงก์ HTTPS ใน `staffPortalUrl`, `performancePortalUrl`, `privacyUrl` และ `termsUrl` เมื่อลิงก์ว่าง หน้าเมนูจะแสดงข้อความแจ้งสถานะ

## 5. ทดสอบการใช้งานสองฝั่ง

เปิดคนละเบราว์เซอร์หรือใช้หน้าต่างส่วนตัวแยกจากหน้าต่างปกติ ให้บัญชีบุคลากรยื่นคำขอ จากหน้าบัญชี HR กดปุ่มลูกศรวงกลม **โหลดข้อมูลล่าสุด** แล้วเปิดคิวเพื่อรับเรื่อง ขั้นตอนถัดไปคือแจ้งพร้อมรับ พร้อมไฟล์ PDF ทดสอบ เมื่อกลับมาหน้าบุคลากรให้กดโหลดข้อมูลล่าสุดเพื่อดูผล

| ทดสอบ | ผลที่ตรวจได้ |
| --- | --- |
| เข้าใช้ด้วยบุคลากรอีกคน | เห็นคำขอ ลายเซ็น ครุภัณฑ์ของตนเอง และคำสั่งที่มีสิทธิ์ |
| เปิดคำสั่งทั่วไปและคำสั่งเฉพาะบุคคล | บุคลากรเห็นคำสั่งทั่วไปและคำสั่งที่ส่งให้ตนเอง เจ้าหน้าที่ HR ดูรายการเพื่อจัดการได้ |
| ลงทะเบียนซ้ำ หรือจองที่นั่งสุดท้ายพร้อมกัน | ระบบใช้ข้อจำกัดไม่ซ้ำและปรับยอดที่นั่งในธุรกรรมฐานข้อมูลเดียวกัน |
| HR สองคนเปิดคำขอเดียวกัน | เมื่อคนแรกเปลี่ยนสถานะแล้ว การบันทึกด้วยสถานะเดิมต้องโหลดรายการใหม่ |
| ดาวน์โหลดเอกสาร | เจ้าของคำขอเปิดไฟล์ของรายการที่พร้อมรับหรือรับแล้วได้ เจ้าหน้าที่ HR ที่มีสิทธิ์ดูได้ |
| พิมพ์เอกสาร | เปิด **รายละเอียด → พิมพ์ใบรับคำขอ** เลือกเครื่องพิมพ์หรือ Save as PDF ในเบราว์เซอร์ |

### การดูแลไฟล์แนบ

ชื่อวัตถุ PDF อยู่ในรูป `<รหัสคำขอ>/<รหัสไฟล์>.pdf` ระบบแนบไฟล์ขณะเปลี่ยนเป็นสถานะพร้อมรับ ถ้าอัปโหลดสำเร็จแต่บันทึกสถานะไม่สำเร็จ เช่น เจ้าหน้าที่สองคนทำพร้อมกัน อาจมีไฟล์ที่ยังไม่ผูกกับคำขอ เจ้าของคำขอเปิดไฟล์ลักษณะนี้ไม่ได้ ผู้ดูแลตรวจค่าคอลัมน์ `public.hr_requests.document_path` เทียบกับชื่อใน bucket ก่อนจัดการไฟล์ตกค้างผ่าน Storage

### ถ้าพบปัญหา

| อาการ | ตรวจจุดนี้ |
| --- | --- |
| หน้าจอยังขึ้น “โหมดทดลอง” | ตรวจ `mode` ใน `web/config.js` ที่เปิดอยู่ แล้วรีเฟรช |
| เข้าสู่ระบบแล้วแจ้งว่ายังไม่มีสิทธิ์ | ตรวจว่ามีอีเมลตรงกันใน Auth และรันไฟล์ 04 ให้บัญชีนั้นแล้ว |
| ตารางไม่พบหรือสิทธิ์ไม่พอ | ตรวจ Project URL, Data API schema, ผลการรันไฟล์ 01 และบทบาทผู้ใช้ |
| เลือกสังกัดไม่ได้ | ตรวจว่ารันไฟล์ 03 ในโครงการเดียวกัน และมีเส้นทางสังกัดครบ 4 ระดับ |
| แนบเอกสารไม่ได้ | ตรวจไฟล์ 02 ใช้ PDF ไม่เกิน 5 MB และเปิดคำขอที่อยู่สถานะกำลังตรวจสอบ |
| แก้ชื่อในหน้าข้อมูลส่วนตัวไม่ได้ | คำนำหน้า ชื่อ นามสกุลมาจากทะเบียน ให้ผู้ดูแลแก้ใน `hr_profiles` ส่วนตำแหน่งและสังกัดเจ้าตัวแก้จากหน้าเว็บได้ |

## 6. จัดเก็บซอร์สโค้ดด้วย GitHub เมื่อได้รับอนุมัติ

เปิด Terminal ในโฟลเดอร์ที่มี README และเก็บเฉพาะประวัติบนเครื่องก่อน

```bash
git init -b main
git add .
git status
git commit -m "Initial RMUTI Khon Kaen personnel MIS"
```

เมื่อต้องการส่งซอร์สขึ้น GitHub ภายหลัง ให้สร้าง repository ว่างของหน่วยงาน เช่น `rmuti-kkc-personnel-mis` เลือก Private ตามนโยบายผู้ดูแล ตั้งค่า URL ของ repository ที่สร้างจริง แล้วจึงส่ง commit ขึ้นไป

```bash
git remote add origin https://github.com/YOUR-ACCOUNT/rmuti-kkc-personnel-mis.git
git push -u origin main
```

เก็บไฟล์ 04 ใน Git เป็นฉบับตัวอย่าง อีเมล ชื่อบุคลากรที่ใช้จริง ไฟล์ PDF ลายเซ็น และรหัสผ่านให้กรอกหรือจัดเก็บในระบบที่จัดเตรียมไว้โดยตรง การเผยแพร่เว็บเป็นอีกขั้นเมื่อวิทยาเขตอนุมัติ ไฟล์ที่ใช้สำหรับเว็บจริงอยู่ภายใน `web/` ทั้งหมด
